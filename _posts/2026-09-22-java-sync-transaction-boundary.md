## 一个反复出现的坑

做后端的同学几乎都踩过一类问题：本地缓存一把 `synchronized` 锁，方法上加了 `@Transactional`，单测一切正常，可一上生产、一遇到重试和并发，数据就莫名其妙地重复落库。

我在一次线上问题复盘中，把这个坑完整地记录了下来。它不是什么高深的并发理论，恰恰是因为"看起来都对"——锁也加了，事务也加了，顺序也写了——才最容易被忽略。

> 核心结论先放这里：**当你同步锁内部的临界区，依赖的是事务包裹下的数据状态时，必须保证同步锁的范围大于等于事务的范围。锁不能比事务更早释放。**

## 事故现场：一次回传重试造成的脏数据

事情发生在一次模型训练结果的回传重试流程里。业务上，系统会把训练好的模型应用回传到下游，并在失败时进行重试。这段逻辑的代码结构大致是这样的：

```java
@Transactional
public void callbackRetry(Task task) {
    // ... 一些前置处理
    synchronized (lock) {
        // 真正的回传 + 落库逻辑
        repository.save(record);
    }
    // ... 方法返回，事务才提交
}
```

直觉上，这段代码没毛病：进了同步块，别的线程就进不来，`save` 完了再出块，事务最后提交，"原子性"好像也有了。

但线上的实际表现是：**下游重试触发后，同一条回传数据被多次落库，产生了脏数据。**

问题出在哪？就出在**同步锁的范围小于了事务的范围**。

注意上面代码里那个括号——`synchronized` 块写在 `@Transactional` 注解的方法**内部**。锁在同步块结束时就释放了，可此时方法还没返回，事务还**没有提交**。于是出现了一个致命的时间窗口：

1. 线程 A 进入同步块，执行 `save`，退出同步块释放锁；
2. 事务尚未提交，A 还在方法尾部执行其他逻辑；
3. 线程 B 拿到了刚刚释放的锁，进入同步块；
4. B 读到的是 A **尚未提交**的数据状态（取决于隔离级别，甚至可能读不到 A 的改动，从而判定"还没回传过"）；
5. A、B 各自走完事务，各自落库，重复写入发生。

也就是说，**你以为锁保护的是"从读到写的整段业务状态"，实际上锁保护的窗口比事务窗口短了一截**。多出来的这一截，就是并发失控的自由地带。

## 为什么会这样：从 Spring 事务的本质说起

要理解这个问题，得先想清楚 `@Transactional` 到底是什么。

Spring 的声明式事务本质上是**基于 AOP 代理**实现的。当你调用一个被 `@Transactional` 标注的方法时，真正先执行的是代理逻辑：

- 方法被调用前：开启事务，从连接池拿到数据库连接，并把连接绑定到当前线程（ThreadLocal）；
- 目标方法执行：业务逻辑跑在这个绑定好的连接上；
- 方法正常返回：代理负责提交事务；
- 方法抛异常：代理根据异常类型决定回滚。

关键点在于：**事务的边界由代理决定，它包住的是"整个目标方法的调用"。** 而 `synchronized` 是 JVM 层面的语法糖，它只认识自己那对花括号。

这两者谁包谁，完全取决于你怎么写：

- 当 `synchronized` 在 `@Transactional` 方法**外面**：线程先拿锁 → 进方法开事务 → 提交 → 出方法 → 释放锁。锁包住了事务，安全。
- 当 `synchronized` 在 `@Transactional` 方法**里面**：代理先开事务 → 进方法 → 拿锁 → 放锁 → 出方法 → 提交事务。锁在提交之前就放了，危险。

很多人下意识地把锁"就近"加在共享资源访问的代码周围，结果刚好选了危险的那种写法。

## 正确做法：把事务"缩"到锁里面

复盘之后，我们定下的规范做法是——**反转嵌套关系，让锁在外层、事务在内层**。

具体落地很简单：把同步块里的那坨业务代码**抽成一个独立的方法 B**，给方法 B 加上 `@Transactional`，而外层持有锁的方法**不要**加事务注解。

```java
// 外层：负责加锁，不加事务
public void callbackRetry(Task task) {
    // ... 前置处理（无需事务的部分）
    synchronized (lock) {
        transactionalService.doCallbackInTx(task); // 调用另一个 Bean 的方法 B
    }
}

// 内层方法 B：负责事务
@Transactional
public void doCallbackInTx(Task task) {
    // 回传 + 落库逻辑
    repository.save(record);
}
```

这样一来，时序就变成了：

1. 外层方法拿到锁；
2. 调用代理的方法 B，开启事务；
3. 执行业务，落库；
4. 方法 B 返回，代理**提交事务**；
5. 退出同步块，释放锁。

锁的释放，永远发生在事务提交**之后**。临界区看到的数据状态，和事务真正落库的状态是一致的，并发重试就不会再产生重复写入。

这里有一个 Spring 老坑必须提醒：**同类内部调用会让 `@Transactional` 失效**。如果你在同一个类里写 `this.doCallbackInTx(...)`，代理根本不生效，事务形同虚设。所以方法 B 一定要放在**另一个 Bean** 里注入调用，或者自己注入自己（self-injection），又或者用 `TransactionTemplate` 编程式地控制事务边界。这个细节写错，整个重构就白做了。

## 几张可以贴在工位上的检查表

把这类问题沉淀成几条可复用的判断准则：

1. **先问"锁保护的是什么"**：如果你锁内的正确性依赖事务提交后的最终状态，那锁的范围就必须覆盖整个事务。
2. **核对嵌套方向**：`@Transactional` 在外、`synchronized` 在内 → 高危；`synchronized` 在外、`@Transactional` 在内 → 安全。
3. **警惕自调用**：跨 Bean 调用事务方法，否则代理不生效。
4. **分布式场景另说**：单机 `synchronized` 在多实例部署下等于没锁，跨进程的去重要回到数据库唯一约束、分布式锁或幂等消费上去兜底。锁只是第一道防线，落库层面的幂等键/唯一索引不能省。

## 小结

这次事故表面上是"锁加错了位置"，本质上是**对两种并发控制原语的生命周期没有对齐**：`synchronized` 管的是 JVM 内线程进入临界区的时刻，`@Transactional` 管的是数据库连接的开启与提交。两者各管一段，谁先谁后、谁包谁，决定了你的"原子性"到底成不成立。

把锁放在事务的外层，让锁的释放晚于事务的提交，这条经验成本极低，却能挡掉一类隐蔽又难缠的脏数据问题。值得记在笔记里，也值得在 code review 时多看一眼。
