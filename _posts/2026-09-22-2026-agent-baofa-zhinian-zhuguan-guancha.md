2025 年底，几乎所有技术公众号都在喊"Agent 元年"。到了 2026 年，口号少了，真正下场做的人多了。过去这大半年，我所在的团队一直在工业场景里真刀真枪地做 Agent 落地——不是写 PPT 里的概念架构图，而是把 Agent 接进真实的业务系统、真实的工业流程里。

这篇文章想记录几个从实战里长出来的观察。它们和舆论场上的"Agent 颠覆一切"不太一样，更接近一个工程师每天面对的真相。

## 观察一：人做方案，AI 写代码——Claude Code 成了主力

先说一个最直观的变化。2026 年我参与的新项目，启动阶段的第一件事不是搭环境、不是写 Demo，而是**"熟悉 AI 编程工具"**。这在两年前是不可想象的——那时候 AI 写代码还是"辅助补全"，现在它已经是主力。

我们团队的工作方式发生了一个结构性变化：**人负责做模块方案、做方案评审、做模块合并，而完整方案的代码实现，直接交给 AI 编程工具去执行**。流程变成了：先拆模块 → 评审模块方案 → 合并方案 → AI 生成完整代码。

这件事的影响比表面上大得多。它意味着工程师的核心价值，正在从"写代码的能力"转移到"定义问题、拆解方案、审查结果的能力"。代码本身不再是瓶颈，瓶颈变成了：你能不能把一个模糊的业务需求，拆成 AI 能准确执行的模块方案？

## 观察二：Agent 爆发的真正底座是"本体"，不是大模型本身

第二个观察，可能是这一年最颠覆我认知的一件事。

外界谈 Agent，焦点永远在大模型上——参数多大、推理多强、上下文多长。但我们在工业场景做下来发现：**Agent 能不能真正落地，瓶颈根本不在模型，而在模型脚下那层"语义层"——也就是行业里说的 Ontology（本体）**。

我们整个系统的设计，是对标 Palantir Foundry 的 Ontology 规范来做的。要补齐的模块包括：对象类型与关联类型（Object & Link Types）、动作类型（Action Types）、函数（Functions）、数据层与索引、搜索与发现、本体管理。为什么要做这么重？因为 Agent 要在工业系统里干活，它得先"认识"这个工业世界里的对象——什么是设备、什么是工单、什么是告警、它们之间是什么关系。没有这层本体，大模型就是对着一堆数据表瞎猜。

真正跑通的链路是三方对齐的：**Agent、本体、自动化引擎（Automate）**。本体定义了世界长什么样，自动化引擎负责感知本体的变化、触发对应事件（支持事件、定时、条件三类触发），Agent 则在这个框架里被调用。当一个 Action Type 或 Function Type 从草稿审批为激活状态时，系统会自动把它注册成 Agent 可用的 Tool——Agent 由此获得了在这个世界里"动手"的能力。

这才是工业 Agent 的真面目：**不是让大模型凭空变聪明，而是给它一个结构化的、可信的、和现实世界对齐的语义底座**。

## 观察三：MCP 把企业系统变成 Agent 可调用的工具

第三个观察，关于 MCP（Model Context Protocol）。

2026 年，MCP 从一个技术社区里的小众协议，变成了企业内部系统对接 Agent 的标准动作。我们做的事情很直接：**把业务 API 包装成 MCP Server**。

听起来简单，但这里面有大量脏活累活——业务 API 的描述要补全、接口列表要整理成规范的 MCP 接口清单、技术方案要过评审。本质上，MCP 解决的是一个"接口语言"的问题：过去企业系统的 API 是给人调用的，文档写得好不好、调不调得通，全靠开发和测试人肉对接；现在有了 MCP，系统能力第一次有了一种 Agent 能理解、能自动发现、能安全调用的标准封装。

可以这么说：**MCP 是 Agent 时代企业系统的"插座"**。没有这层插座，每个 Agent 都得重新写一遍对接代码；有了它，系统能力变成了即插即用的标准件。

## 观察四：踩坑实录——Agent Tool 的能力，比想象中弱得多

前面说的都是架构，现在泼一盆冷水。真正做下来，最大的坑是：**Agent Tool 的实际能力，远没有宣传里那么强**。

举个真实的例子。我们做了一个"遍历对象关联"的 Agent Tool，本意是让用户用自然语言查询对象之间的关系。结果上线后问题不断：用户用自然语言说"帮我查一下这个设备关联的工单"，Agent 到底该传什么参数进去？是传对象的唯一标识，还是传名称？自然语言里的表达和工具定义的入参之间，存在一个巨大的鸿沟——**用户说的话，和工具期望的参数，对不上**。

排查到最后，结论很扎心：不是我们的实现有 bug，而是**自然语言到工具入参的适配能力本身就不够**。Agent 经常因为猜不准参数，导致查询始终失败。还有一个专门做异常创建的 Agent Tool，因为是未完成版本，能力实在太弱，最后直接被下线去掉了。

这件事给我的教训是：**2026 年谈 Agent 落地，不能只看"能调通"，要看"调得准不准"**。一个 Tool 能不能被稳定地用起来，取决于它的入参设计是否足够清晰、是否足够贴近用户的自然语言表达。这不是模型再迭代一版就能解决的问题，而是工程设计问题。

## 观察五：大模型从架构中心，降级为"工具"

最后一个观察，有点反直觉。

年初我们做仿真方向的探索时，原本想让大模型驱动整个流程——给仿真模型喂数据、对比真实场景、由用户选择策略、再调参仿真。但做着做着发现：**大模型在这套架构里，其实根本不需要占据中心位置**。

最终的判断是：**大模型降级成了"PLC 的替代品"——它只是一个通过显值提供使能值的工具**。甚至一度考虑把大模型从架构里拿掉，直接跑仿真执行引擎，支持多个仿真并行。真正有价值的沉淀，不是大模型本身，而是围绕它建起来的那套知识库——通过设备文件、异常告警图片、说明性文档构建起来的知识体系，让仿真模型的经验能够被沉淀、被复用。

这个观察和整个行业的趋势是吻合的：**2026 年，大家终于祛魅了**。大模型不再是那个"无所不能的中央大脑"，它回归成了一个工具——和数据库、和消息队列一样，是架构里的一个组件，有它擅长的地方，也有它的边界。真正值钱的，是围绕它建起来的本体、知识库、工具封装、自动化链路。

## 写在最后：2026 不是元年，是祛魅之年

如果让我用一句话总结这一年的实战感受：**2026 不是 Agent 的爆发元年，而是 Agent 的祛魅之年。**

舆论场上还在喊颠覆，但真正下场做的人已经知道：Agent 要落地，靠的不是更大的模型，而是更扎实的本体、更标准的工具协议、更贴近业务的工程设计。人负责想清楚，AI 负责写出来；大模型负责理解，本体负责约束。这个分工一旦跑顺，Agent 才真正从演示走向生产。

我自己的判断是：接下来一两年，Agent 领域的竞争，不会再是模型参数的竞争，而是**谁能把语义底座打厚、把工具封装做标准、把自然语言和工程现实之间的鸿沟填掉**的竞争。

这场仗，才刚刚开始。
