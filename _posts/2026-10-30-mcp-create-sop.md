## 引子：四次返工，四个借口

我一共做过四个 MCP 项目。

- [mcp_mubu](https://github.com/qingyuanLee/mcp_mubu)：把一个只能网页点的文档工具，接成 LLM 能直接写的文档库。
- [mcp_processon](https://github.com/qingyuanLee/mcp_processon)：让 LLM 自己在原生画布上摆形状、连线条，输出可编辑的在线图。
- [wechat-mcp](https://github.com/qingyuanLee/mcp_wechat)：用自己的公众号，一句话把文章写进草稿箱。
- [qq-notes-exporter](https://github.com/qingyuanLee/qq-notes-exporter)：把十年 815 条邮箱记事和 1283 张会烂掉的外链图片，搬进本地 Markdown。

四个项目，四套完全不同的接口，四种失败方式。但如果把返工的原因摊开看，会发现**借口各不相同，病根是同一批**：

- 工具长得像 HTTP 接口，LLM 要填八个参数才会用 —— 抽象错了。
- 写入返回 `version: 12`，浏览器白屏转圈一整天 —— 验收点错了。
- 只在我自己机器上能跑，别人装不上 —— 交付漏了一层。
- 重跑一次，多出一份同名文档 —— 我忘了 Agent 会重试。

这四个坑各踩一次之后，我把它们连同修法一起写成了一个小仓库：
[mcp_create.skills](https://github.com/qingyuanLee/mcp_create.skills)（一个可直接安装的 Agent Skill）。
这篇文章是它的叙事版：**判断是怎么形成的，而不是我写了什么代码**。

![](/img/posts/mcp-create-sop-cover.jpg)

## 一、先纠正一个误解：MCP 不是 API 包装器

我最初的理解是"把接口包一层，让 AI 能调"。这个理解能跑通 demo，然后必然卡住。

因为 API 的抽象单位是**资源**（user、draft、chart），而 LLM 的动作单位是**意图**（"把这篇文章发出去"、"画个架构图"）。
这两者不在同一个粒度上。你按 API 包，LLM 就在拼装你的接口；你按意图包，LLM 才在使用一个能力。

判断标准很粗暴：**一个工具如果需要 LLM 填 6 个以上参数才能用，层次就错了。**

反面教材来自我自己。ProcessOn 的第一版我是这么设计的：

```text
create_chart → add_node(id, x, y, w, h, anchors, fill, ...) → add_edge(from, to, ...) → set_style(...)
```

让 LLM 算坐标、算宽高、算锚点角度。它算得出来，但每次都算错一点，而且中间态会崩（画到第三个节点时图就废了）。

改成：

```python
draw_flowchart(chart_id, nodes, edges, theme="techblue")
```

坐标交给代码算（分层布局 + 碰撞分离），LLM 只负责说"有哪些节点、谁连谁"。一次就对。

**两个永远成对的工具，本质上应该是一个工具。** 这条后来帮我砍掉了三分之一的设计。

## 二、第二个纠正：不要让 LLM 直接产出复杂结构

这是我在画图项目里最得意的一个决定。

自然语言 → 图形，最直觉的做法是让 LLM 直接输出图形 JSON：节点数组、坐标、样式、连线。
结果字段错漏率极高，而且人没法读、没法改、没法进版本库。

正解是插一层**中间表示**：让 LLM 写 Mermaid。

```text
1. design_diagram(prompt)      → 拿到 Mermaid 草稿（不出图）
2. 【这里不调任何工具】我直接改 Mermaid：增删节点、补标签、调分层
3. render_mermaid(code)        → 渲染成可编辑的在线图
4. 重复 2–3 直到满意
```

第 2 步是全部价值所在。LLM 写 Mermaid 的准确率，比拼 30 个字段的图形结构体高一个量级；
而且 Mermaid 是人能读、能改、能 diff 的。**把"改"的权力留在文本层，而不是图形层。**

同一个模式后来复用了三次：
Markdown → 公众号 HTML（而不是让 LLM 写内联样式）；
大纲 → 思维导图；
SQL → 报表。

凡是"LLM 要产出复杂结构"的地方，都值得问一句：**有没有一种它有语感的 DSL？**

## 三、最贵的一课：写入成功 ≠ 能被使用

这一课花掉的时间，比前两个项目加起来还多。

ProcessOn 支持三种编辑器协议，我复刻完字段之后，架构图能画出来了。然后我想加"分组"——
给节点打上 `group`，自动画一个虚线大框把它们包起来，表达分层。

服务端返回得很干脆：

```json
{"version": 12}
```

明确成功。然后浏览器打开，**白屏，转圈，永远转**。

我用了四轮才定位到真因：

| 轮次 | 我的假设 | 结果 |
|---|---|---|
| 1 | 形状名 `container` 触发了前端分派 bug | 改成普通 rectangle，还是白屏 |
| 2 | 手写矩形少了轮廓信息 | **真根因**：漏了 `path` 字段（矩形轮廓的绘制指令），前端拿不到就整个崩 |
| 3 | 浅色衬底用 update 消息回写 | 又白屏 —— updates 的对象格式我从没抓过包，凭想象拼的 |
| 4 | —— | 放弃回写，颜色靠 create 时一次性设定 |

注意第 1 轮和第 3 轮的共同点：**我在没有样本的情况下发明了字段**。
而服务端对"多一个字段"和"少一个字段"同样宽容——它只负责存，不负责渲染。

从这一次长出两条铁律，后来每个项目都在用：

> **一、服务端返回成功，只代表"存下来了"。渲染在你没测的那一端。**
>
> **二、没有抓包样本的字段，一律不许发明。**

第二条还衍生出一个工程动作：**每个写工具必须配一个读工具**。

```python
processon_create_chart(...)      # 写
processon_get_chart_def(id)      # 读回来，逐字段比对
```

微信项目里也一样：`create_draft` 之后必须能 `get_draft`，看一眼标题长度、图片数、正文有没有被截断。
这不是"多写一个工具"，这是**验收**。

## 四、验收金字塔：四层，缺一层就有一类 bug 永远抓不到

后来我把验收整理成一个固定结构，每次照抄：

```text
L0  纯函数单测     布局算法 / 格式转换 / HTML 渲染（不联网，最快）
L1  whoami         进程起得来吗、配置读到了吗、认证通了吗
L2  smoke          一条读 + 一条写，产物落盘能查（<10 秒跑完）
L3  读回           写完立刻 get_* 拉回来，断言字段
L4  真消费端       浏览器打开 / 后台看草稿 / Visio 打开导出的文件
```

**L1 是最容易被跳过、也最该第一天就写的。** 没有 `whoami` 的 MCP 项目不可维护——
用户说"用不了"的时候，你连坏在哪一层都不知道。

**L4 不能省。** 有一批 bug 只在真消费端暴露：

- 导出的 `.vsdx` 必须用 Visio / drawio **真打开**，不是解压看 XML。我曾经因为"大矩形容器盖住了节点"，
  让消费端把被盖住的节点识别成子形状、直接丢弃——文件结构完全合法，只是少了几个节点。
  `attribute.container` 这个字段我以为能判断容器，实测全是 `False`，判断错了。
- 公众号草稿必须进后台真看一眼渲染。Markdown 转 HTML 的样式问题，只有在真编辑器里才现形。
- 分享链接必须用**未登录的浏览器**打开一次。你自己的会话是已登录的，测不出权限问题。

## 五、默认所有调用都会被重放

人会点一次，Agent 会：重试、中断后重跑、把同一段计划执行两遍、超时后怀疑失败再来一次。

所以"重复执行不产生第二份垃圾"不是优化，是**正确性**。

三个模式，按优先级：

```python
ensure_folder_path(path)   # 逐级 find-or-create，已存在就复用
ensure_chart(title, fid)   # 同名已存在 → 删除（进回收站）→ 重建
share_chart(permanent=True)  # 天然幂等：重复开启返回同一个链接
```

第一版我全用的裸 create，结果是重跑一次就多一个 `文档(1)`、`架构图(2)`。
用户（也就是我）第三次打开时已经分不清哪个是新的。

配套的还有两条：**删除一律进回收站**，不做硬删；
**不可逆动作必须卡人**——微信的发布走"草稿 → 人工预览 → 发布"，个人号（无认证权限）干脆只到草稿。

这里还牵出一个有意思的设计：错误信息不是写给日志看的，是**给人做决策**的。

```text
❌ 48001 api unauthorized
✅ 该接口需要认证账号；个人订阅号请到「订阅号助手」App 手动发表（文章已进草稿箱）
```

同一条错误，第二种写法把"下一步做什么"直接给了用户。这不是体验优化，是能力边界的一部分。

## 六、交付漏了一层：为什么 90% 的 MCP 项目"别人装不上"

MCP server 写完、跑通、推到 GitHub，我以为交付完成了。然后换台机器装，装不上。

缺的是**两个不同读者的两份文档**：

| 层 | 产物 | 读者 | 只回答一个问题 |
|---|---|---|---|
| 能力层 | MCP server | 宿主程序 | 有哪些动作、怎么执行 |
| 使用层 | `SKILL.md` | LLM | 什么时候用、参数怎么填、哪里会翻车 |
| 安装层 | 连接器配置指南 | 人 | 怎么装到我这台机器上 |

`SKILL.md` 里我踩过的坑是：只列工具，不写顺序。LLM 会把工具当菜单随机点。
必须写出**工作流和判断**，包括"这一步不调工具"这种话——上面那个 Mermaid 的例子，
如果不写"第 2 步你自己改"，LLM 就会一路调工具到黑。

安装层的坑更土，但 100% 会撞上：

- 连接器的命令必须填 **`.venv\Scripts\<svc>-mcp.exe` 绝对路径**，不能填 `python -m xxx`——
  连接器的工作目录和你终端里不是同一个。
- **连接器拉起进程时不读项目 `.env`。** 环境变量必须在连接器里显式填。这一条我排查了很久，
  因为本地命令行一切正常。
- 平台侧前置条件（微信 IP 白名单、账号认证等级）要写在文档第一屏，否则会被当成代码 bug 排查一遍。

## 七、20 条死路里，最值钱的几条

那个仓库里有一份 `07-failure-atlas.md`，20 条，格式统一：**症状 → 真因 → 动作**。
卡住时先搜症状关键词，命中就直接用动作，不再做根因推理。

挑几条最有普适性的：

**分页用 `total` 做终止条件。**
记事本接口返回 `total_affected_count`，我拿它做循环条件。它有时**只在第一页返回**，
第一次遇到 `total=0`，直接死循环。"815 条只拉到 700 条"和"跑不完"是同一个字段的两个方向。
唯一可靠的终止条件：**本页数量 < page_size 就停**。

**缺一个"看起来没用"的参数，偶发失败。**
记事本接口要求每次请求带 `r` = 毫秒时间戳 + 5 位随机数。不带不报错，只是**偶发**拿到空 body。
这类参数在抓包时最容易被当成垃圾删掉。所以删减测试要一个一个来，不能一把梭。

**边下载边改，改坏了没法回滚。**
1283 张图片，第一版是边下边把正文里的 URL 替换成本地路径。跑到第 400 张时程序崩了，
正文已经被改了一半，而原始数据没存——只能重爬（有些链接已经取不到了）。
正解是**清单（manifest）作为唯一事实来源**：先把所有图片下完、记进清单，最后一步统一替换。
原始数据永不修改，这是一切"可回滚"的前提。

**间隙算成了反号。**
两个盒子的间隙 = `max(左) - min(右)`，我写成了 `min(右) - max(左)`。
重叠时算出负数，我以为"间隙为负就推开"，结果越推越远，坐标从几百爆炸到十万。
修复本身一行，找到它花了两小时——后来每个布局改动都配一个断言脚本，打印"冲突数 / 最小间距 / 坐标范围"。

**能力根本不在服务端。**
想导出高清图，我先写了浏览器自动化 + 轮询，时序极脆。后来发现服务端有导出管线
（`exportType=jpghd` + CDN 轮询拿 URL），直接拉字节就行。
另一个反例：`.vsdx` 导出，我 grep 了 850KB 的前端 SDK，**没有任何 `/api` 调用**——
转换全在浏览器里由 mxGraph 完成。结论：这个文件只能自己生成（最后用 `zipfile` 手写了一个最小 OPC 生成器）。

**先判断能力在哪一层，比写代码重要。**

## 八、收敛成五条

四个项目跑完，能带走的就这五句：

1. **写入成功 ≠ 能被使用。** 渲染在你没测的那一端。每个写工具必须配一个读回工具。
2. **没抓包样本的字段不许发明。** 少一个 `path`，前端整图白屏，服务端依然报成功。
3. **抽象到"用户会说的那句话"为止。** 需要 LLM 填六个参数的工具，层次就错了。
4. **默认所有调用都会被重放。** 幂等是正确性，不是优化。
5. **负知识优先写。** 死路清单比成功路径值钱，而且只有踩过的人才写得出来。

还有一条不算原则，算经验：**"好不好看"往往决定有没有人用。**
架构图从"节点挤成一团"打磨到"分层对称 + 虚线分组 + 浅色衬底"，中间是六轮迭代。
技术上这些都是坐标计算，但它决定了我自己愿不愿意打开这个工具。

## 最后

这些方法被整理成了一个可以直接安装的 Skill：
**[mcp_create.skills](https://github.com/qingyuanLee/mcp_create.skills)**

```text
mcp-create/
├── SKILL.md                  五条铁律 + 八步 SOP
├── references/               侦察 / 工具设计 / 认证传输 / 幂等验证 / Skill 层 / 发布 / 20 条死路
└── assets/templates/         pyproject、server 骨架（认证自动重登 + ensure 幂等 + 双传输）、
                              README / SKILL / 连接器配置指南模板
```

把 `mcp-create/` 拷到 `~/.workbuddy/skills/` 下就能用。下次说"帮我做个 MCP server"，
它会先问你三个问题（高频吗、结构化吗、产物能被人改吗），然后按八步走，卡住时翻死路清单。

四个项目的完整拆解在 [docs/case-studies.md](https://github.com/qingyuanLee/mcp_create.skills/blob/master/docs/case-studies.md)。

写这套东西最大的收获，不是"我总结出了方法论"，而是发现**这四个项目的失败方式高度重复**。
这意味着下次做第五个，我不需要更聪明，只需要照着清单走一遍。
